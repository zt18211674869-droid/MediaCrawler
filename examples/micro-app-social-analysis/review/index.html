把“有效帖子”写成可以执行的规则

有效证据不足推广无关待核对

有效帖需要讲清：用户做过什么，以及至少一个具体体验点。

后续灵光研究明确了两条基本要求：

  • 作者亲自生成、修改或使用过应用，能指出具体任务或操作。
  • 至少讲清一个与应用生成相关的体验点。

例如，“修改后桌面快捷方式仍打开旧版”，能定位到具体环节；“这个 AI 太强了”，还不足以说明应用生成体验。

帖子状态处理原则
有效有亲身使用及具体体验，进入分析
相关但体验证据不足保留相关线索，不作为使用效果证据
推广有明确依据时标注，不因正向或带链接就认定推广
无关排除同名产品或范围之外的内容
待核对详情失败，或关键证据在未读取的图片、视频里

有效帖再标注正向、负向、混合或中性。同一帖可以包含多个方向不同的体验点。

讲述提示
短帖只要说清一个具体问题，也可以有效。一篇帖子即使最终满意，也可能经历过很多次失败，所以我既保留整帖态度，也记录各个环节的具体反馈。

一个边界案例：是灵光的帖子，但没有应用生成体验

《辅导作业｜讲题讲 3 遍娃还是懵，多亏有它》

作者描述拍照获取数学题讲解、换角度拆解知识点。内容确实涉及灵光，也有具体使用场景，但没有描述生成、修改或运行一个应用。

如果只按产品名和正负向筛选，这类内容就容易混进来。这个例子也说明，需要进一步明确：这次要分析的是产品整体体验，还是应用生成这一项能力？

看完灵光后的反思：把研究问题放到搜索之前

看完灵光结果后，我发现：只有正负向帖子，分析仍然缺少目标。

因此，我补上了更前置的一步：先明确研究问题，再组织后续搜索和分析。这个要求是在试用过程中逐渐形成的，后来成为复用方法时的起点。

对应用生成研究，我希望回答：用户能否从提出需求，走到持续使用一个应用？

历史讨论中，我提出按步骤研究：

“需求提供……修改，然后分发以及再次编辑。”

由此形成应用生成的观察框架：

01需求表达需求是否清楚，产品是否理解
02首次生成等待时间、初版符合程度
03UI 与交互布局、组件、页面跳转
04修改迭代修改生效且不破坏旧功能
05运行发布功能可用，他人可以打开
06持续使用数据保留、重开和再次编辑

成本、易用性和可靠性可以贯穿各个环节一起记录。

讲述提示
这一步是看完灵光后补上的。我发现，好评和差评只是材料，还需要研究问题来组织分析。后来就把确认研究目标放到舆情搜索之前，沿生成、修改、发布和持续使用去看反馈，分析才有明确方向。

结果怎样进入报告：从帖子到体验发现

用“任务—操作与结果—用户影响”组织证据。

日常价值｜从自己的生活任务出发

原帖：跟风灵光，手搓了四个应用。

用户经历：做菜谱、打卡、运动及猫咪健康记录；打卡用得最多，还在使用中给运动工具加了倒计时。同帖也提到上传图片经常死机。

研究判断：部分用户把生成应用带入日常任务。满意和摩擦可以出现在同一篇帖子中，需要按具体体验拆开记录。

持续使用｜工具为什么让人愿意回来

原帖：读博日常：逐渐恢复的学习秩序感。

用户经历：作者制作科研待办工具，填写任务和预计完成时间，完成任务后获得一朵花，认为奖励有助于坚持计划。

研究判断：除生成效果以外，还应观察用户是否愿意持续录入，以及应用怎样承接日常习惯。单个案例不能推断总体留存提升。

可靠性｜再追查修改、版本和数据

其他样本还出现多轮修改布局仍不满意、桌面入口仍打开旧版、已录入记录消失等自述。它们分别指向修改成本、更新一致性与数据保存，应进入后续复现清单。

我的后续追问是：

“负向帖子不多有什么原因么？”

实际核对发现，负向主情绪数量和使用中遇到问题的数量并不相同。

原因本次研究中的表现
问题属于其他功能登录、PPT、普通代理任务等，不计作应用生成体验
卡点藏在混合或满意帖中多轮失败，最终完成；整体正向但修改费力
关键内容未能读取只能从视频或配图判断的内容，保留待核对
时间范围有边界历史故障不能当作近期体验
搜索与作者存在偏向综合排序、成果分享和少数作者集中发帖影响样本

处理方式：保留真实缺口，不降低标准凑满 10 篇；同时提取混合帖里的具体卡点。

讲述提示
“正负各 10 篇”是代表案例的采集目标。数据不足时，我需要知道不足在哪里。比起强行补齐数量，更有价值的是把问题发生的环节和后果讲清楚。

最终方法论：先定目标，再用工具深入问题

01明确研究目标先确定要回答的问题
02筛选有效帖子搜索、核对、校准筛选标准
03围绕问题继续洞察按线索补搜、查评论、找反例

起初只是想试试功能，目标没有定清楚，是这次走弯路的原因。

先搜到正负向帖子以后，我发现仍然不知道怎么分析、怎么支持报告，于是才回头补充研究目标。下一次应该把目标确认放在最前面。

  • 明确研究目标： 要支持什么判断？研究产品整体还是某项能力？覆盖哪个渠道与时期？
  • 筛选有效帖子： 用工具搜索与核对，保留相关、亲历且有具体体验的原帖；通过少量样例校准筛选标准。
  • 围绕问题继续洞察： 从有效帖发现线索，再按问题补搜、查评论、找反例，解释发生条件和影响。

提效做法是首次阅读就提取证据、去重后分批并发、只针对缺口补查，并复用同一份证据记录完成统计、精选和报告。没有对照计时，不宣称具体提速比例。

讲述提示
我一开始只是想试试这个功能，没有把目标定清楚，所以走了一些弯路。后来发现先有研究目标，才知道哪些帖子有效；有效帖里又暴露出新问题，再围绕这些问题继续洞察，工具才真正服务于研究。

这次使用带来的收获

生成出来 → 修改到满意 → 实际用起来

工具扩大了搜索范围；研究问题、筛选标准和证据核对，让结果能进入报告。

最终留下三类产出：

  • 研究材料： 原始命中、去重台账、有效帖证据和代表原帖。
  • 研究发现： 分环节的认可点、使用障碍、反例及待验证问题。
  • 复用方法： 筛选规则、提示词、Markdown 方法文档和 Skill。

本次最值得继续验证的判断是：

生成出来、修改到满意、实际用起来，是三道不同的门槛。

下次使用可以沿用这条顺序：

明确研究目的 → 小范围试搜 → 检查并修订标准 → 扩大采集 → 按缺口补搜 → 核对证据并形成报告。

结束讲述建议

对我来说，这次最有价值的变化，是从“帮我找一些好评和差评”，走到了“围绕一个研究问题，整理能回查的使用证据”。工具能协助完成很多搜索和整理工作，我们仍需要判断这些证据说明了什么，以及下一步应该验证什么。

请实际使用 **GUAIKEI MCP**，在小红书研究 **灵光、秒哒、Today、Muse、WorkBuddy 五款产品的「应用生成」功能真实用户体验**，交付逐产品全样本统计、代表原帖和跨产品研究洞察。

**本次研究对象是应用生成这一特性，不是产品整体能力或品牌口碑。**重点回答：用户能否把需求生成应用，能否修改到符合预期，以及生成后的应用能否实际运行、分享和持续使用。

## 一、研究范围与产品识别

开始前确认当前会话能调用 GUAIKEI 的小红书工具。如果工具未加载、认证失败或连接失败，报告具体错误并暂停。切换到浏览器或通用网页搜索前，先征得我同意。

先核对五款产品的名称、别名、开发方及应用生成功能名称，尤其确认 Today、Muse 等容易重名的产品。无法确定具体指代时，先向我确认，不要把同名产品混入样本。

纳入以下体验：

- **需求表达与首次生成**：从自然语言、截图或参考界面生成应用，需求理解、生成速度、首次成功率。
- **UI 与交互生成**：布局、视觉效果、组件、页面跳转、交互完整性，以及与需求或参考图的符合程度。
- **修改与迭代**：能否理解修改意图、局部修改是否准确、是否破坏已有功能、多轮修改后的稳定性。
- **功能与业务逻辑**：表单、计算、数据存储、查询、登录或其他任务逻辑是否真正可用。
- **运行、发布与持续使用**：预览与实际运行是否一致，分享、部署、权限、跨设备、版本更新、数据保留及持续使用情况。
- **生成过程中的成本与门槛**：仅纳入直接影响生成、修改、发布或使用应用的额度、付费、报错和技术门槛。

不纳入与应用生成无直接关系的通用问答、文案、图片、搜索、办公辅助等评价。产品整体“好用”“不好用”不能直接作为该功能的证据。WorkBuddy 等产品的普通办公自动化体验，也不能自动算作应用生成体验。

允许纳入有交互或功能的网页应用、小工具及原型；单张 UI 图片、静态页面展示需单独标记，不能当作“应用实际可用”的证据。

## 二、逐产品、逐批搜索与核对

1. 调用 `xiaohongshu_note_search`，每批设置 `limit=100`。若工具实际限制更低，如实记录请求参数和实际返回数。
2. 五款产品分别建立样本池，第一轮采用结构一致的中性关键词，例如：
   - 「灵光 应用生成 实测」「灵光 闪应用 实测」
   - 「秒哒 应用生成 实测」
   - 「Today 应用生成 实测」
   - 「Muse 应用生成 实测」
   - 「WorkBuddy 应用生成 实测」

   核对功能名称后可使用准确别名。记录搜索词、排序方式和检索时间。
3. 保留每篇笔记的 ID、`xsec_token` 和原帖链接。每批返回后按笔记 ID 去重，先用标题和摘要排除明显无关或推广内容，再对其余候选调用 `xiaohongshu_detail` 读取正文。
4. 主要证据在配图或视频里时，核对实际可获取的内容。详情失败或关键证据无法读取，标为「待核对」，不能仅凭标题推断。
5. 需要补充评论区反馈时，调用 `xiaohongshu_comment`。区分评论者亲身体验、求链接和泛泛评价；评论单列，不混入原帖作者体验或有效帖数量。
6. 完成当前批次核对和统计后，再按发现调整关键词，例如「产品名 UI 修改」「产品名 生成失败」「产品名 数据保存」「产品名 发布 分享」「产品名 应用 实际使用」。
7. 将**中性检索**与**正负向定向补搜**分开记录。五款产品先完成可比的基础检索，再针对证据缺口补搜，避免只围绕个别产品深挖。
8. 每款产品争取精选正向、负向各 10 篇。数量不足时继续补搜；若限流、可访问内容不足或持续没有新增有效帖，如实报告已核实数量、检索覆盖和缺口，不降低标准、不凑数。

## 三、有效性、情绪与证据判定

有效帖需同时满足：

- 作者亲自使用目标产品生成、修改、运行或使用过应用，能指出具体任务或操作。
- 至少讲清一个与应用生成相关的具体体验点。

短帖只要讲清一个点，也算有效。提示词、运行截图、修改前后对比、同任务跨产品对比和评论复现可提高证据质量。

排除明显广告、官方宣传、活动招募和互赞导流。纯成品展示、链接分享、教程步骤及未提供亲身体验的功能介绍，归为「相关但体验证据不足」。不能仅因内容正向或附有链接就判定推广，需记录判断依据。

每篇去重后的帖子标一个状态：

**有效｜相关但体验证据不足｜推广｜无关｜待核对**

每篇有效帖根据作者对**应用生成功能**的整体体验标一个主情绪：

**正向｜负向｜混合｜中性**

不要用作者对产品其他能力的态度代替本研究的情绪判断。

同时记录：

- 产品及功能名称
- 用户任务、应用类型和使用场景
- 具体操作与体验
- 发生环节
- 实际影响：完成任务、继续修改、改用其他工具、放弃、持续使用等；未交代则写「未说明」
- 证据出处：正文、配图、视频及可定位时间点
- 是否仅展示界面、是否证明功能可运行、是否有持续使用证据

同帖可记录多个方向不同的体验点。例如“默认 UI 满意，但逻辑反复修不好而放弃”，可以主情绪为负向，同时记录「UI 正向」「修改迭代负向」。

跨产品帖子按笔记 ID 建立唯一记录，仅在对某款产品具有独立有效证据时，进入该产品样本。整体独立笔记数与各产品样本数分别报告，说明后者相加可能大于前者。

## 四、全样本统计

每批统计一行，包含：

产品、搜索词、检索类型（中性／定向）、排序方式、请求数、实际返回数、批内去重数、跨批新增数、成功读取正文数、五种筛选状态数量、有效帖四类情绪数量、本批新增有效帖数。

批次筛选状态和情绪数量以该批去重后的命中帖为口径；本批新增量单独计算，避免重复累计。

逐产品跨批去重后汇总：

- 总请求数、实际返回数、去重帖数
- 五种筛选状态数量
- 有效帖四类情绪数量与占比
- 各生成环节的有效证据覆盖量
- 仅界面展示、已验证运行、已有持续使用证据的数量

计算：

**有效率 = 跨批去重后的有效帖数 ÷ 跨批去重后的返回帖数**

**每请求 100 条的平均产出 = 跨批去重后的有效帖数 ÷ 总请求条数 × 100**

中性检索与定向补搜分别呈现；两者重叠的笔记单独说明。所有确认有效的帖子均进入统计，不能只统计精选帖。

说明这些数字反映的是本次检索样本，不能直接解释为全平台用户满意度。跨产品情绪占比比较需同时展示样本量、检索方式和证据覆盖差异，不据此直接排名产品优劣。

## 五、代表帖精选

**每款产品分别精选正向、负向各 10 篇，五款产品目标共 100 篇。**不足时报告实际数量及缺口，不用混合或中性帖补齐。

优先选择讲清以下链条的帖子：

**做了什么 → 产品生成或修改得怎样 → 应用实际能否用 → 对用户结果有什么影响**

证据质量相近时，再参考点赞、收藏和评论数。

每篇列出：标题、作者、日期、互动量、用户任务、发生环节、最有价值的具体体验、实际影响、证据出处及原帖链接。互动量注明抓取时间；缺失字段写「未获取」。

使用工具返回的真实 ID 和 `xsec_token` 生成链接，不编造参数：

`https://www.xiaohongshu.com/explore/{id}?xsec_token={xsec_token}`

## 六、研究洞察

### 1. 逐产品洞察

每款产品总结用户最认可的 3–5 个体验点和最常遇到的 3–5 个卡点。证据不足时少列，不凑数。

每个点注明：

- 有多少篇有效帖提到，占该产品有效帖的比例
- 具体任务、发生环节及实际影响
- 代表原帖
- 是否存在相反证据及适用条件

同一篇可计入多个体验点，同一体验点内只计一次。

### 2. 跨产品对比

以「需求理解、首次生成、UI 与交互、修改迭代、功能逻辑、运行发布、持续使用」为框架，比较五款产品。

每项区分：

**有证据支持的优势｜有证据支持的问题｜证据不足**

重点解释：

- 哪些体验是应用生成的共性问题，哪些更集中于某款产品？
- 哪些产品能帮助用户从“生成出来”走到“实际用起来”？证据到达哪一步？
- 哪些任务容易一次成功，哪些需要反复修改或最终放弃？
- UI 完成度与功能可用性是否存在落差？
- 修改过程中是否出现旧功能受损、版本不同步或数据丢失？
- 哪些体验促成持续使用，哪些只停留在尝鲜和展示？

只有存在同任务、相近条件的直接证据时，才作明确的性能优劣判断；其余标注为样本观察或待验证假设。

### 3. 产品机会

提出 3–5 个围绕应用生成的产品机会。每项写清：

**用户问题 → 原帖证据及数量 → 当前影响 → 改进方向 → 可验证指标**

将原帖事实、研究归纳和产品建议明确区分。所有结论可追溯到原帖，不用产品宣传或站外转述填补体验证据。
